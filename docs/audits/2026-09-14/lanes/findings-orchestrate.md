## Findings (ranked)

### 1. P2 — `reverseBioMemo` is a process-global, never-reset, unbounded promise cache: stale team evidence and unmetered reuse across scans and tenants
**Files:** `server/adapters/x.ts:2328-2345`; `server/orchestrate.ts:3845-3847` (only `resetDefiLlamaScanMemo` / `resetFollowScanMemo` are called at scan start); `resetReverseBioMemo` is called only from tests.
**Mechanism:** `discoverReverseBioFromTwitterapi()` memoizes the *promise* by subject handle with no TTL, no size bound, and no scan-boundary reset. Every later `runAudit` of the same handle in the same warm instance (rescan hours later, a different organization's scan, a gap re-run) gets the first scan's resolved object back, ignoring the new `subjectName`/`projectBio` arguments. Because the promise is cached, zero twitterapi calls happen and zero `recordTwitterapi` rows land in the second scan's AsyncLocalStorage ledger.
**Failure scenario:** Tenant A scans `@proj` at 09:00; `@alice`'s live bio says "Co-founder @proj" -> team row with `artifact_verified: true`, evidence `their current X bio states "..."`. Alice edits her bio at 10:00 ("Left proj"). Tenant B (or A, forced rescan) scans `@PROJ` at 11:00 in the same warm container: the report again asserts Alice's *current* bio carries the founder claim (freshness lie; `enrichFirstPartyTeamAvatars` then enriches her as first-party), the run's provider ledger under-reports spend (tenant A paid, tenant B's ledger shows nothing for this lane), and the Map grows one entry per distinct handle for the life of the process. The other memos in the same file are explicitly bounded (`lastTweetsMemo` 10 min / 64 entries, `followMemo` 30 s + reset); this one is not.
**Fix:** Call `resetReverseBioMemo()` next to the two existing resets in `runAuditWithLedger` (orchestrate.ts:3845), and give the memo the same TTL+cap as `lastTweetsMemo` (or key it per run).
**Confidence:** high. **Repro:** confirmed by probe (second call with a changed bio stub made no fetch, returned the identical object, its ledger was empty).

### 2. P2 — Private ("incognito") scans leave a durable, org-visible trace in `entity_facts`
**Files:** `api/audit.ts:344-353` (passes `organizationId: auth.organizationId` unconditionally; `private` only skips `persistServerDossier` at :373); `server/orchestrate.ts:5554-5578` (`writeEntityFacts` whenever `options.organizationId` is set); `server/entityStore.ts:65-107` (upserts `handle`, `display_name`, `facts`, `audit_count+1`, `updated_at`); `server/adapters/basicFacts.ts:4552-4587` (`loadReusableBasicFacts` reads them back and emits "Recent verified facts reused ... Argus verified recently").
**Mechanism:** The private flag governs persistence of the report only. The knowledge-base write-back, the `audit_count` increment and the `readPriorOutcome` lookup all run for private runs too.
**Failure scenario:** An analyst runs a private scan of a sensitive subject. `entity_facts` for the org now holds that subject's handle/display name/verified facts with a fresh `updated_at`; with `ARGUS_ENTITY_REUSE=on` a colleague's later scan of the same handle streams a step revealing the subject was "verified recently" by the org. The client contract for private runs (`src/lib/runner.ts:33`: "never persisted, logged, graphed") is violated server-side. Also applies to the always-private embedded project-account audit inside token investigations (arguably wanted there), so gate on the request flag rather than on `organizationId`.
**Fix:** Thread `privateRun` into `RunAuditOptions` and skip `writeEntityFacts` (and optionally `readPriorOutcome`) when private.
**Confidence:** high (static). **Repro:** not run.

### 3. P2 — Watchlist sweep silently no-ops on the documented "preferred" Supabase credential; its budget and ledger are also wrong
**Files:** `server/sweep.ts:35-40` vs `api/_auth.ts:41-43`, `server/cache.ts:14-25`, `server/entityStore.ts:14-24`, `.env.example:87-90`; `api/sweep.ts:12` (`maxDuration: 120`); `server/sweep.ts:23,93-98`.
**Mechanism:** Every other server module accepts `SUPABASE_SECRET_KEY` (sb_secret_*) first and omits `Authorization: Bearer` for it. `sweep.ts` reads only the legacy `SUPABASE_SERVICE_ROLE_KEY || SUPABASE_SERVICE_KEY` and always sends `Bearer <key>`. `.env.example` calls the legacy var a migration fallback to "remove once rotated".
**Failure scenario:** After the rotation the example file prescribes, "Sweep now" returns `{checked: 0, note: "no backend configured"}` with HTTP 200 and no error; drift/ring alerts never fire while the UI reports a completed sweep. Secondary: the route allows 120 s but runs up to 15 *sequential* `auditToken` calls with no `deadlineAt`, so a full watchlist overruns the function ceiling and is killed before persisting alerts; and it calls `src/token/audit.auditToken` directly (not `server/tokenAudit`'s `withCostLedger` wrapper), so its provider calls land in the module-global `fallbackState` (`server/cost.ts:68-70`) and are never attributed to the org.
**Fix:** Use `serviceCredentials()`/the shared header helper in sweep.ts; pass a `deadlineAt` derived from the route budget and cap checks by remaining time; wrap in `withCostLedger` and record the ledger against the org.
**Confidence:** medium-high (the no-op depends on the deployment having rotated to `SUPABASE_SECRET_KEY`; the mismatch itself is certain). **Repro:** not run.

### 4. P2 — Gap investigations re-run the entire unscoped cold intake, spending outside the authorization and starving the authorized adapters
**Files:** `server/orchestrate.ts:4141-4294` (cold-intake block; `coldIntake` at :994-1909 has no `capabilityIsAuthorized`/`adapterIsAuthorized` gate — the only intake gate is `projectTokenPass` at :4144/4153); `api/gap-investigation.ts:449-461` (budget 180-540 s, `analystDeadlineAt = start + budget - 30 s`); `src/lib/investigationRuntime.ts:76-89` (`collectionReserveMs = min(250 s, 0.6 * (budget - 30 s))`).
**Mechanism:** `authorizedResearchScope` restricts adapters, signal passes and post-passes, but the intake wave (8 concurrent discovery searches at :1096-1133, claimant-bio confirmation, Serper founder follow-up, team-identity enrichment, affiliation corroboration, orientation, operator-launch history) runs in full for every gap re-run. For a 300 s budget the collection deadline is `start + 108 s`; intake alone routinely exceeds that.
**Failure scenario:** Analyst authorizes an `official_facts`-only follow-up to close a basic-facts gap. The run re-spends discovery (Grok/Serper/twitterapi; the 24 h cache helps only if the source scan was same-day and the handle casing matches — see #5), reaches `collectionOverBudget()` before the lanes, records every adapter including `basic-facts` as `skipped: collection time budget reached` (:4376-4378), and persists a `partial` proposal that never attempted the authorized work while `observedCostUsd` may exceed the accepted ceiling. This compounds known #358 rather than duplicating it: the deadline is short *and* the pre-deadline work is not the authorized work.
**Fix:** Gate cold-intake sub-waves on capability (`people_and_control` for team discovery, `portfolio_and_outcomes` for affiliations, etc.) or, for scoped runs, hydrate intake from the frozen source version and run only `resolveProfile`; alternatively exclude intake time from the scoped collection budget.
**Confidence:** high on mechanism, medium on typical timing. **Repro:** not run.

### 5. P3 — Handle casing is preserved into every x.ts cache key, so the embedded project-account audit and a direct audit of the same subject never share the 24 h cache (double spend)
**Files:** `src/lib/resolveInput.ts:126,134` (case preserved); `src/data/evidence.ts:1172-1176` (`profile.handle` keeps caller casing); `server/adapters/x.ts:1466,1560,2002,2161,2822,2866` (`affil:${h}`, `team-x-v2:${h}`, `reverse-role:${h}`, `founder-followup:...`, `adverse:...@${h}`, `manip:${h}` with `h` un-lowercased) vs `server/adapters/basicFacts.ts:1514,1668,1746` (lowercased); `src/lib/runner.ts:44,73` (UI lowercases) vs `src/lib/investigation.ts:314,426` (`projectX` from DexScreener/CoinGecko, e.g. `@Uniswap`, passed as-is).
**Failure scenario:** A token investigation embeds a scan of `@Uniswap`; ten minutes later the analyst opens the project directly (`uniswap`). Every intake Grok/Serper search and the adverse sweep miss the cache and are re-bought. No wrong evidence, but repeatable paid re-spend and inconsistent cache behaviour between the two entry points.
**Fix:** Lowercase the handle once at `runAudit` entry (or in `resolveInput`) and build all cache keys from the normalized handle.
**Confidence:** high. **Repro:** confirmed (`resolveInput("@Uniswap").ref === "Uniswap"`).

### 6. P3 — `withProviderDeadline` aborts an adapter's fire-and-forget cache writes the moment the adapter returns
**Files:** `server/providerDeadline.ts:5-20` (`finally { clearTimeout(timer); controller.abort(); }`), `:24-28` (`deadlineFetch` joins the ALS signal); `server/cache.ts:53-66` (`cacheSet` uses `deadlineFetch`, best-effort catch); `server/adapters/x.ts:161,236`, `server/adapters/groundedSearch.ts:571`, `server/adapters/basicFacts.ts:1591` (`void cacheSet(...)` immediately before returning).
**Mechanism:** The ALS store propagates into detached promises created inside `a.run(ctx)`. When the adapter's last provider call finishes, `void cacheSet` starts a 4 s Supabase write; `runAdapter` resolves, `finally` calls `controller.abort()`, and the write is aborted and swallowed.
**Failure scenario:** The final Grok/Claude search of an adapter (typically the most expensive) is never cached, so the next rescan within 24 h re-buys it. Intermediate writes usually complete because later provider calls keep the adapter alive; the tail write is lost most of the time.
**Fix:** In `withProviderDeadline`, abort only from the timer (not on successful completion), or have `cacheSet` use `globalThis.fetch` rather than `deadlineFetch`.
**Confidence:** medium (timing-dependent; mechanism certain). **Repro:** not run.

### 7. P3 — Scan receipts are marked `degraded` / `provider_incomplete` on healthy runs (ledger status semantics)
**Files:** `server/cost.ts:95-100` (`aggregateStatus` returns `partial` for any mix, including succeeded+cached); `server/adapters/defiLlama.ts:413,425,431` (memo hits recorded as `cached` on the same `audit-links`/`tvl` op as live `succeeded` reads); `server/adapters/x.ts:85-86,152-158` (`audit_spend_ceiling` and `empty_output` recorded as `partial` attempts; the ceiling path increments `grok.calls` with no HTTP call); `api/audit.ts:412-427` (`providerIssue` = any line `failed` or `partial` -> `status: "degraded"`, `failureCode: "provider_incomplete"`).
**Failure scenario:** One DeFiLlama parent doc served from the 30 s memo plus one live child read, or a single Grok call that legitimately returned no text, flips the scan receipt to `degraded/provider_incomplete` although every provider answered. Once the Grok spend ceiling is hit, every subsequent `grokSearch` call books a phantom `partial` attempt and increments `grokCalls`, so the Finalize "N calls" line and the receipt over-count.
**Fix:** Treat `cached` as success in `aggregateStatus`; do not increment `grok.calls` on the ceiling short-circuit; derive `providerIssue` from `providerFailureLines` or `line.failed + line.partial > 0` rather than the aggregate status.
**Confidence:** high. **Repro:** aggregation rule confirmed by probe (succeeded + cached -> `partial`).

### 8. P3 — `recordProtocolSecurityIncidentFindings` dedups on (source_url, date) and drops distinct incidents
**Files:** `server/orchestrate.ts:3050-3062`.
**Mechanism:** Dedup key is `protocol.sourceUrl` (same for every incident of the protocol) plus `incident.date ?? protocol.capturedAt`. Two exploits on the same day, or any two undated incidents (both fall back to `capturedAt`), collapse to one finding.
**Failure scenario:** A protocol with two undated DeFiLlama hack rows publishes one `ProtocolSecurityIncident` finding; the second amount/technique is silently lost from the analyst packet and the persisted report.
**Fix:** Key on the incident row (date + amount + technique/classification) rather than the page URL.
**Confidence:** high. **Repro:** not run.

## Looked suspicious, verified correct (do not re-check)

- **SSE stream correctness** (`api/audit.ts:298-327,454-455`; `src/lib/live.ts:73-128`): heartbeat comment lines are ignored by the client regex; `event:`/`data:` writes are synchronous pairs so the interval cannot interleave; JSON payloads contain no raw `\n\n`; client inactivity watchdog (90 s) > heartbeat (15 s); `credits`/`persistence` events are safely ignored; `res.write` after client disconnect does not throw, and the run intentionally continues to persist.
- **Thrown adapter -> false complete?** No. `runAdapter` catch (`orchestrate.ts:4413-4419`) records the provider row `failed`; check ids the adapter never recorded stay `unknown` (`server/checks.ts:530-537`), and `clearanceCoverage` treats `unknown` as unrecorded, so never-waive rows hold completeness at `partial`. Same for `collection_deadline_reached` thrown after a completed run: the result is discarded conservatively (`basicFactsCompleted` -> false -> `unavailable`, never `checked-empty`).
- **Promise.all in cold intake** (`orchestrate.ts:1005-1019,1096-1133`): every member catches transport/JSON errors and returns null/[]; no reachable rejection, so no lane-killing or unhandled-rejection path. `adverseSignalsAndTooling` uses `allSettled` per target correctly.
- **`withWallClockBox` (#378):** main now aborts the controller in `finally` and races the timer (`server/boundedProvider.ts:3-22`); `<= 0` budget returns null immediately. Fixed.
- **Cost ledger isolation** (`server/cost.ts:67-75`, `server/orchestrate.ts:5584-5586`, `server/tokenAudit.ts`): `runAudit`, gap-investigation person and token paths all run inside `withCostLedger`; only `api/social-activity.ts` and the sweep (#3) fall through to `fallbackState`, and nothing reads that state back (metering gap itself is known #356/#379).
- **Lane provider disjointness for attempt deltas** (`ADAPTER_PROVIDERS`, `orchestrate.ts:336-345`): grounded search's extractor defaults to Grok (`groundedSearch.ts:483-486`), so `["grok","cache"]` filters still observe the calls; only with `ARGUS_PROVIDER_FALLBACKS=on` and Grok down would `adverse-sweep`/`portfolio-verification` provider rows read `skipped` while the check rows stay correct. Cosmetic; not filed.
- **Deadline math** (`api/audit.ts:349-351`, `orchestrate.ts:3854-3865`, `agent.ts:4451-4476`): analyst start-by 510 s, collection stop 260 s, graph window to 320 s, analyst self-caps to the remaining window, finalization worst-case (prior outcome 10 s + bundle 15 s + usage batch 16 s + activation 10+10 s + audit log 8 s) fits the 90 s reserve. Pre-adapter intake and post-collection passes remain ungated by the collection deadline; that is known #320/#357 and still open on main.
- **`recordProviderUsageBatch` limits** (`api/_cache.js:186-199`): distinct `provider|op` keys in the codebase are ~45 (ops are static literals or a 2-value suffix / twitterapi endpoint path), so the 200-line and duplicate-line throws are not reachable.
- **Other provider cache keys** (`basicFacts.ts:1514`, `socialActivity.ts:630`, `offchain.ts:323-337`): include handle/website/question fingerprint/provider/15-min window as appropriate; service-only table.
- **Entity-store reuse** (`basicFacts.ts:4552-4587`): behind `ARGUS_ENTITY_REUSE=on`, org-scoped, per-predicate TTLs, projection facts and legal events excluded, always-refresh predicates re-searched; reused facts keep their original `capturedAt`.
- **Repair pass** (`basicFacts.ts:4848-4890`): the three verification passes over the same leads are CPU-only re-checks; `fetchOnce` memoizes fetches so no re-spend, and `resolveBasicFactCandidates` dedups sources by URL (`:3544-3546`), so repeated verification does not inflate corroboration counts. Only `evidenceAttempts` carries cosmetic duplicates.
- **`evalHarness`** swaps `globalThis.fetch`/`process.env` process-wide; unsafe under concurrency but offline tooling only. **`captureTimestamp`** correctly freezes to the recording boundary in replay.
